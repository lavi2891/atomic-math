# Content Authoring Standard v1

המסמך הזה הוא רשימת הבדיקה המחייבת לכתיבת שאלות ב־Atomic Math. העיקרון המנחה: כל שאלה צריכה להפיק עדות נקייה עבור ה־`Skill` שאליו היא משויכת, וכל אובייקט מתמטי שמוצג לתלמיד צריך לעבור דרך `ContentRenderer`/KaTeX.

## 1. כללי מיקוד פדגוגי

- מגדירים תחילה מה בדיוק התלמיד צריך לדעת או לעשות, ורק אחר כך בוחרים ניסוח ומספרים.
- השאלה חייבת לבדוק את ה־`Skill` הרשום בה. אין לייחס ל־`EQ_ADD` חישוב חיסור רגיל, ל־`ALG_SUBSTITUTE` חישוב ביטוי בלי פעולת הצבה, או ל־`INT_MUL` כפל חיובי בלבד.
- ידע מקדים יכול לתמוך במשימה, אך אסור שהוא יהיה מקור הקושי העיקרי או הסיבה היחידה להצלחה.
- ב־Skills של מספרים מכוונים שולטים במבנה הסימנים במפורש בעזרת גדלים חיוביים ותבנית סימנים; לא מגרילים טווח רחב ומקווים שיתקבל מספר שלילי.
- השוואה מציגה במפורש את שני האובייקטים. משוואה מציגה את השוויון שנפתר. הצבה מציגה גם את ערך המשתנה וגם את הביטוי שאליו מציבים.

## 2. כללי Difficulty ו־Band

- `A/B/C/D` מתארים שינוי פדגוגי אמיתי, לא מקום פנוי בתשתית.
- `difficultyFeature: "magnitude"` מותר כאשר גודל המספרים מגדיל באמת את עומס החישוב. הטווח של Band קשה חייב להיות דטרמיניסטי: `hard.min >= easy.max` לפחות בפרמטר הקושי המרכזי.
- במיומנויות מבניות מעדיפים `difficultyFeature: "structure"`: יותר פעולות, סוגריים, מיקום נעלם אחר, הפשטה סימבולית או מספר משתנים גדול יותר.
- באלגברה, שוויון וחוקי פעולות, מספרים גדולים יותר אינם ברירת מחדל לקושי. עוברים ממקרה מספרי ל־symbol אחד, לכמה symbols או להנמקה מבנית.
- לכל משפחה מבנית מרובת Bands נדרש `metadata.structuralStage` שונה בכל Band.
- אין לשנות את יעד ה־Skill כדי לייצר קושי. למשל, ב־`AR_MUL_F_2_5_10` הגורם האטומי נשאר תמיד אחד מ־`2, 5, 10`.
- אם אין הבדל משמעותי, מסירים או מאחדים Band. אין חובה מלאכותית להחזיק ארבע רמות.

## 3. כללי Generator

- מבנה מספרי שגרתי נכתב כ־generator. אין לשכפל שאלות קבועות שנבדלות רק במספרים.
- `exprTemplate`, `params`, `constraints`, `contentFamily`, `difficultyFeature` ו־`structureKey` מתארים את המבנה הפדגוגי האמיתי.
- משפחות בעלות משמעות שונה נשארות נפרדות: sharing לעומת grouping, הרחבת שבר לעומת צמצומו, וסוגי סימנים שונים במספרים מכוונים.
- אותו seed חייב להחזיר אותו instance. `sampledParams`, `renderedExpression` והפרטים ב־Question Review חייבים להתאים זה לזה.
- פרמטר שנדגם חייב להשפיע בפועל על הביטוי, הניסוח, האפשרויות או וריאציה גלויה אחרת; אין להוסיף פרמטרי דמה כדי ליצור שונות.
- `singleChoice` מחזיר בדיוק תשובה נכונה אחת. אם כמה תשובות נכונות בכוונה, משתמשים ב־`multiChoice`.
- ב־`AR_FACTORS_MULTIPLES` מנסחים במפורש אם מחפשים גורם או כפולה. כאשר כמה מהאפשרויות תקפות, משתמשים ב־`multiChoice` ובניסוח “איזה מהמספרים הבאים...”.

## 4. כללי שאלה Curated

- `curated` מיועד למקרה שבו הניסוח, הייצוג או הערכים המדויקים הם האובייקט הפדגוגי.
- מספרים מתמטיים קבועים דורשים `curationReason` מאושר: `misconception`, `edge-case`, `representation`, `regression` או `deliberate-example`. הערך הכללי `other` אינו מספיק עבור מספר קבוע.
- כאשר קיימים מספרים קבועים, `curationJustificationHe` מסביר מדוע דווקא הערכים האלה נחוצים. “דוגמה נוחה” או “מספר שרירותי” אינם הצדקה.
- אין להמציא `exprTemplate` לשאלה קבועה רק לצורכי תצוגת review.

## 5. כללי Distractor ו־Misconception

- כל מסיח מייצג שגיאה סבירה: היפוך יחס, כלל סימנים שגוי, השמטת מקדם, התעלמות מסוגריים, שימוש בפעולה הגלויה בלי בדיקת הקשר וכדומה.
- לכל מסיח נדרשים `misconceptionId` ו־`misconceptionRationale`; לתשובה הנכונה אסור להצמיד metadata של misconception.
- אין להשתמש במספר אקראי שגוי רק כדי למלא אפשרות רביעית.
- validator בודק כפילויות טקסטואליות ושוויון מתמטי בין מסיח לתשובה נכונה. אילוץ generator צריך למנוע התנגשויות אפשריות מראש.

## 6. כללי Math rendering ו־RTL

- ביטויים, משוואות, אי־שוויונות, שברים, משתנים, מספרים מכוונים, סמלים ואפשרויות מספריות נכתבים כ־`{ kind: "math", latex }`.
- בכתיבה דרך `authoredStudentContent`, עוטפים אובייקט מתמטי ב־`[[...]]`. `authoredChoiceContent` ממיר אפשרות מתמטית טהורה אוטומטית.
- גם נתון מספרי שמשמש לפתרון בעיה מילולית הוא inline math: `יש [[12]] כדורים`.
- מספר שלילי לעולם אינו נשען על כיוון RTL של text. משתמשים ב־math segment ובמינוס מתמטי.
- אין להציג `5 + -3`, `7 - -2` או `4 × -5`; כותבים `5 + (-3)`, `7 - (-2)`, `4 × (-5)`.
- אפשרויות `singleChoice` ו־`multiChoice` חייבות לתמוך בשילוב עברית ו־inline math דרך `ContentRenderer`.

## 7. כללי ניסוח לבעיות מילוליות

- הניסוח קצר, קונקרטי, מכבד גיל ומסתיים במשימה מפורשת.
- כל גודל הדרוש לפתרון מסומן כ־inline math; מספור UI מקרי יכול להישאר text.
- שומרים על ההבחנה בין קבוצות שוות, חלוקה שווה וקיבוץ. ההקשר אינו קישוט אלא חלק ממשמעות השאלה.
- משתמשים במונחים מדויקים: “`x` הוא משתנה” או “האות `x` מייצגת ערך מספרי”, ולא “`x` הוא מספר”.
- נמנעים מקטעי משפט, מכמות מבוקשת מרומזת ומפרטים סיפוריים שאינם תורמים למתמטיקה.
- בהקשרי כפל משתמשים בשמות עצם קונקרטיים ושואלים במפורש על הכמות הכוללת. בחלוקה שווה מציינים את היחידה בתשובה המבוקשת; בקיבוץ שואלים במפורש כמה קבוצות או מכלים דרושים.
- שאלת סימן שואלת על “סימן המכפלה” או “סימן המנה”. שאלת השוואה מציגה את שני הערכים ואת המקום שבו יש להשלים `<`, `>` או `=`.

## 8. כללי Review ו־re-review

- URL מאתחל את ה־filters בלבד. ניווט בין definition, Bands ו־samples אינו משנה את ה־filters.
- סדר הסקירה הוא definition → כל ה־Bands הנתמכים → definition הבא.
- אישור family generated דורש ביקור ואישור של כל ה־Bands הנתמכים; `needs-fix` או `rejected` ב־Band אחד מונעים סטטוס משפחה מאושר.
- כל `QuestionReviewRecord` חדש שומר `definitionVersion`. הגדרה עם tag בשם `requires-rereview` מתייחסת לרשומה מגרסה ישנה כ־unreviewed.
- אישורי legacy ללא `definitionVersion` שניתנו לבנק עד v3 נשמרים כל עוד ה־definition לא שונה. כל שינוי חדש מועלה ל־v4 ומעלה, ולכן דורש רשומת review עם גרסה תואמת.
- שינוי פדגוגי, שינוי תשובה, שינוי מבנה, שינוי טווח או שינוי student-facing מחייב העלאת `version` והוספה/שימור של `requires-rereview`.
- שינוי טכני שאינו משנה את התוכן הנבדק אינו מחייב פסילת אישור; יש לתעד את ההחלטה ב־audit.

## 9. כללי Validation

`npm run validate-content` הוא שער blocking עבור:

- math גולמי בתוך text, מספר שלילי גולמי, רצף סימנים או שבר פגום;
- תשובות כפולות, תשובה נכונה חסרה, מסיח ששווה מתמטית לתשובה נכונה או metadata חסר למסיח;
- curated עם מספרים קבועים ללא סיבה והצדקה;
- generator לא דטרמיניסטי, ללא שונות מספקת או עם `sampledParams` שאינם תואמים להגדרה;
- Band magnitude שאינו מתקדם דטרמיניסטית ו־Band structure ללא `structuralStage` ייחודי;
- סטייה ממשפחת fact אטומית, instance חיובי בלבד ב־Skill מכוון, או משימת equation/substitution/comparison שאינה מציגה את יעד ה־Skill.
- כפל מכוון אינו משתמש בשני גורמים דו־ספרתיים שרירותיים. Band מתקדם רשאי להשתמש במבנה mental כגון `×10`, `×11`, עשרות שלמות או ריבוע מכוון, או לעבור להפשטה סימבולית.

מספר שמופיע בתוך text רגיל מסווג כאזהרת authoring: יש להחליט אם הוא נתון מתמטי שחייב לעבור ל־inline math או פרט מקרי שמותר להשאיר כטקסט.

לפני commit של תוכן מריצים `npm test`, `npm run lint`, `npm run build`, `npm run validate-content` ו־`git diff --check`.

## 10. דוגמאות לדפוסים טובים ורעים

| רע | טוב | הסיבה |
|---|---|---|
| `INT_MUL` עם `{a}*{b}`, כאשר שניהם חיוביים | `(-{m})*{n}` עם `m,n` טבעיים | מבנה הסימנים מבטיח עדות על כפל מכוון |
| `EQ_ADD` עם prompt “חשבו: 12-5” | “איזה ערך משלים את `□+5=12`?” | השוויון והנעלם הם יעד ה־Skill |
| `ALG_SUBSTITUTE` עם חישוב ביטוי מספרי בלבד | “אם `x=4`, מה מתקבל לאחר הצבה ב־`3x`?” | פעולת ההצבה מוצגת במפורש |
| Bands של חוק סימנים שנבדלים רק ב־`max` | A: שלילי×חיובי; B: שלילי×שלילי | הקושי נובע ממבנה ולא ממזל |
| `(-27)×(-34)` כדי “להקשות” חוק סימנים | `(-20)×(-7)` או שאלת סימן סימבולית | עומס כפל ארוך אינו העדות המבוקשת |
| `יש 12 כדורים ומחלקים ל-3` כ־text | `יש [[12]] כדורים ומחלקים ל־[[3]]` | הנתונים עוברים דרך KaTeX ונשמר RTL תקין |
| מסיח `17` אקראי | מסיח שמחבר במקום לכפול עם `misconceptionId` מתאים | המסיח מספק עדות אבחונית |
| ארבע שאלות curated זהות עם מספרים אחרים | generator אחד עם `exprTemplate` ו־`params` | המבנה נשמר ללא magic numbers |
| אישור ללא גרסה | `QuestionReviewRecord.definitionVersion === definition.version` | שינוי תוכן מחזיר את ההגדרה ל־re-review |
